---
title: Runes and automation
description: Turning demonstrated magical practice into inspectable spell-engine behavior.
---

A rune encodes a bounded action the mage has learned through practice. A spell engine composes runes into an observable process over admitted tools, materials, conditions, and destinations.

Automation follows the same authority as manual work. It cannot create matter, ignore custody, reach through a missing route, perform an unknown practice, or repair an invalid output after the fact. A manual action, scheduled process, imported blueprint, and background continuation all use the same commit primitive.

## Progression

Early runes repeat one gesture. Later systems sense conditions, select admitted substitutions, route outputs, coordinate facilities, pause on unsafe state, and publish useful signals. Complexity buys expressive capability, not exemption from material constraints.

The interface exposes inputs, outputs, capacity, ownership, current step, failure state, and provenance. Players should be able to understand why a machine is waiting without reading a private implementation log. Exact rune syntax and simulation granularity remain prototype work.
